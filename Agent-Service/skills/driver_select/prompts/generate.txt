## 작업

### Step 1. Driver 후보 검토
- 모든 NFR 는 기본적으로 Driver 후보
- FR 중 **구조적 복잡도가 큰 기능**(분산/이벤트 중심/대량 처리 등)을 Driver 후보에 포함
- CNST 중 **아키텍처 선택을 제한하는 제약**(기술 스택/규정/플랫폼)을 Driver 후보에 포함

### Step 2. QAD / QAI 평가 (1~5 정수)
- **QAD (Quality Attribute Demand)**: 비즈니스/품질 관점에서 해당 요구가 시스템에 미치는 영향도
- **QAI (Quality Attribute Impact)**: 해당 요구를 만족시키기 위한 기술적/구조적 난이도
- 각 점수에 근거(`rationale`)를 명시 — 단순 추측/임의값 금지

### Step 3. Priority 산정
- 기본 공식: `priority = qad * {w_qad} + qai * {w_qai}`
- 이 값을 각 driver 에 기록

### Step 4. risk / sensitivity
- **risk**: 해당 driver 가 아키텍처 결정에서 유발할 수 있는 위험 (예: "분산 트랜잭션 일관성 난이도")
- **sensitivity**: 설계 결정이 이 품질속성에 얼마나 민감하게 작용하는지 (예: "파티셔닝 전략에 따라 응답시간 2~5배 편차")

### Step 5. Driver 선정
- Priority 상위 순으로 **5~10건 내외** 선정
- 핵심 품질속성을 **고르게 대표**하도록 (한 속성에 편향되지 않게)

### Step 6. 정규화 속성 추출 (중요 — style_define 의 입력)

시스템 전체를 다음 속성 어휘로 정규화해 `normalizedAttributes` 에 기록합니다.
**반드시 아래 어휘만 사용하세요.** 관련 없는 속성은 생략.

허용 속성 어휘 (값은 low/medium/high/required, 또는 각 속성별 고유값):

**품질속성**:
`scalability, modifiability, availability, performance, security, consistency, latency, auditability, debuggability, testability, simplicity, portability, decoupling`

**요구 패턴 / 워크로드**:
`event_volume, async_processing_need, synchronous_low_latency, real_time_processing, read_write_ratio_skewed, sporadic_workload, simple_crud, data_volume, domain_complexity, long_running_job, stateful_heavy, short_lifecycle, long_term_maintenance`

**프론트엔드**:
`large_ui_codebase, polyglot_frontend_tech, strict_ui_consistency, ui_team_independence`

**인프라 / 규모**:
`service_count, multi_cluster, inter_service_traffic_control, observability_requirement, strong_vendor_independence`

**조직 / 운영**:
- `team_size`: small / medium / large
- `ops_maturity`: low / medium / high
- `release_frequency`: low / medium / high
- `team_independent_deploy`: low / medium / high
- `strong_consistency`: low / medium / high  (일관성 요구 강도)

값 체계:
- 3단계: `low` / `medium` / `high`
- 요구 강제: `required`
- 없음/불명: 해당 속성을 `normalizedAttributes` 에서 **생략** (추론 금지)

### Step 7. 문서 작성
`architecture/drivers.md` 본문을 작성합니다. 양식:

---

# Architecture Drivers

## 1. 선정 Driver 목록

| # | Requirement | 타입 | 이슈 키 | QAD | QAI | Priority | risk | sensitivity |
|---|------------|------|---------|-----|-----|----------|------|-------------|
| 1 | (요약) | NFR | FR_NNN/QA_NNN/CNST_NNN | 4 | 5 | 4.5 | (요약) | (요약) |

## 2. Driver 별 상세 근거

### FR_NNN / QA_NNN / CNST_NNN — (이슈 요약)
- **QAD {score} 근거**: ...
- **QAI {score} 근거**: ...
- **risk**: ...
- **sensitivity**: ...

## 3. 정규화된 시스템 속성 (style_define 입력)

| 속성 | 값 | 근거 Requirement |
|------|-----|----------------|
| scalability | high | QA_001, QA_003 |
| team_size | small | (인터뷰 / project-description) |
| ... | ... | ... |

## 4. 선정 편향 점검
- 어떤 품질속성 집합을 대표하는가
- 의도적으로 제외한 후보와 그 이유

## 출력 (반드시 단일 JSON 객체)

{{
  "drivers": [
    {{
      "key": "{code}-27",
      "qad": 4,
      "qai": 5,
      "priority": 4.5,
      "risk": "...",
      "sensitivity": "...",
      "rationale": "..."
    }}
  ],
  "normalizedAttributes": {{
    "scalability": "high",
    "team_size": "small"
  }},
  "document": "전체 drivers.md 본문 (Markdown)"
}}

**주의**:
- 이슈 키는 실제 제공된 Requirement 의 `key` 를 사용 (허구 금지)
- 문서 본문의 "이슈 키" 열에는 해당 Requirement 의 `subkey`(예: FR_001/QA_001/CNST_001)를 사용
- `normalizedAttributes` 의 키는 위 허용 어휘 내에서만 선택

## 환경

- `PLATFORM_API` 기본값: `http://10.211.55.3:44350/api/v2`
- 저장 경로: `business/project-description.md`

## 인자 추출

사용자 메시지에서 다음 값들을 추출해 **먼저** 환경변수로 export 한 뒤 아래 bash 블록들을 실행하라. 누락 시 사용자에게 되물어 확정하라.

- `CODE` — projectCode (예: GOJIRA3)
- `USER` — user (예: batman) — `docs/{user}` 브랜치로 커밋, `X-User-Id` 헤더로 전송

예:
```bash
export CODE="GOJIRA3"
export USER="batman"
```

## 역할

노련한 시니어 기획자. 이 세션 안에서 **에이전트(Claude) 가 직접** 사용자에게 자연스럽게 질문하고 답변을 채팅으로 수집한다. 별도 Q&A 저장소 없음 — 대화 맥락만으로 충분. 답변이 모호/짧으면 재질문. 모든 항목이 충분히 채워지면 마크다운을 작성해 저장한다.

### 범위 원칙 — **무엇을 만들지가 아니라 누가 어떤 가치를 위해 사용하는지**

project-description.md 는 **요구사항 정의 이전 단계의 문서**다. 후속 단계(driver-select → style-define → design-decide)에서 아키텍처 결정을 내리는 입력이 되므로, 여기서 설계 결정을 미리 박아두면 후속 단계의 자유도가 사라지고 추적성도 깨진다. 따라서 인터뷰와 문서화는 다음 원칙을 따른다.

- ✅ **누가 (역할/이해관계자)**, **무엇을 (사용자가 인지하는 행동·결과)**, **왜 (가치/근거)** 를 끌어낸다.
- ✅ 조직·법·외부 환경에서 오는 **제약** (정책/규제/기존 자산/벤더 종속 회피 등) 은 끌어낸다.
- ✅ 사용자 관점의 **품질 속성** (속도/가용성/보안/데이터 주권 등) 은 끌어낸다 — 단, "~ 해야 한다" 형태로.
- ❌ **기술 스택** (어떤 언어/프레임워크/DB) 묻지 않는다.
- ❌ **컴포넌트 분할 / 통신 방식 / 데이터 모델** 묻지 않는다.
- ❌ **아키텍처 결정 요약** 절을 만들지 않는다.

사용자가 자발적으로 기술 결정을 말해도 인터뷰어는 "그 결정으로 풀고 싶은 사용자 문제는 무엇인가요?" 로 한 단계 위 가치를 끌어내 user story 로 재진술한다.

## Step 0 — 기존 문서 확인

```bash
PLATFORM_API="${PLATFORM_API:-http://10.211.55.3:44350/api/v2}"

# docs/{user} 우선, fallback main (스크립트 자동 처리)
DESC=$(bash "${PROJECT_ROOT}/.claude/skills/_scripts/doc-read.sh" "${CODE}" "${USER}" "business/project-description.md" 2>/dev/null || true)
echo "---EXISTING---"; echo "$DESC" | head -80
```

내용이 이미 충분(템플릿 외 실질 30자 이상)이면 사용자에게 "이미 문서가 있습니다. 보강할까요, 새로 작성할까요?" 를 물어본 뒤 선택에 따라 진행. 비었으면 바로 Step 1.

---

## Step 1 — 인터뷰 진행 (에이전트 직접)

### 진행 규칙
1. 먼저 "project-description.md 작성을 위해 몇 가지 여쭙겠습니다" 안내
2. **한 번에 한 질문씩** 자연스러운 말투로 질문
3. 답변이 짧거나 모호하면 **구체적으로 재질문** (예: "조금 더 구체적인 배경이 있을까요?")
4. 답변은 에이전트가 세션 컨텍스트(대화 기록)로만 기억. 중간에 저장 없음.
5. 모든 항목이 충분해지면 사용자에게 "이대로 문서를 생성할까요?" 확인 후 Step 2.

### 질문 항목 (질문 뱅크)

| id | label | 질문 |
|---|---|---|
| background | 과제 배경 | 이 과제를 시작하게 된 배경이나 동기는 무엇인가요? 지금 무엇이 잘 안 되고 있나요? |
| purpose | 과제 목적 | 이 과제가 달성하려는 핵심 목표는 무엇인가요? 성공했다고 판단하는 기준이 있다면 함께 알려주세요. |
| stakeholders | 주요 이해관계자 | 이 시스템을 누가 어떤 상황에서 사용하게 되나요? (직접 사용자 + 간접 영향자 모두) |
| user_stories | 핵심 사용자 가치 | 각 이해관계자가 이 시스템으로 **무엇을 할 수 있길 원하는지**, 그리고 **왜 그것이 가치 있는지** 를 알려주세요. 시스템이 어떻게 만들어져야 하는지가 아니라, 사용자가 인지하는 결과 관점으로요. |
| qualities | 품질 기대 | 사용자가 체감해야 할 품질 수준이 있나요? (응답 속도, 가용성, 보안, 데이터 주권 등 — 정량적이면 더 좋음) |
| constraints | 제약사항 | 조직/정책/외부 환경에서 오는 제약이 있나요? (사내 보안 정책, 기존 자산 호환, 벤더 정책, 규제 등 — 기술 선택은 아님) |

### 질문 가이드라인
- **user_stories 는 가장 시간 들여 끌어내라**. 한 줄짜리 "이슈 관리 기능" 같은 답이 오면 "어떤 이해관계자가 이슈를 어떤 상황에서 어떻게 쓰고, 그게 안 되면 무엇이 곤란해지나요?" 로 재질문.
- 사용자가 "Mongo 를 써야 한다", "React 로 만들어야 한다", "마이크로 서비스로 가야 한다" 같은 **기술/아키텍처 결정**을 답하면 → 그대로 받지 말고 "그 선택으로 어떤 사용자 문제를 풀고 싶으신가요?" 로 한 단계 위 가치를 끌어내 user story 로 재진술. 본인이 강하게 원하면 `constraints` 의 "벤더/플랫폼 제약" 항목으로만 기록.
- 답변에 누락된 **간접 이해관계자**(운영, 보안, 감사, 파트너) 있으면 "혹시 ~ 관점도 고려해야 할까요?" 로 확인.
- 품질 속성(성능/보안/안정성) 암묵 기대가 있으면 정량적 표현으로 끌어낸다.
- 유사 과제 pitfall 이 의심되면 가볍게 짚어 확인.

## Step 2 — 마크다운 초안 작성 (에이전트 추론)

수집된 대화 내용을 아래 구조로 정리한다. **사용자 답변 사실은 보존**, 누락 맥락은 시니어 관점으로 합리적 보강하되 해석임을 드러낸다.

### 문서 템플릿

```markdown
# Project Description

## 과제 배경
(현재 무엇이 잘 안 되고 있는지, 왜 지금 이 과제를 시작하는지를 구체적으로 서술.
누락된 맥락은 시니어 관점에서 보강하되 추정임을 자연스럽게 드러냄)

## 과제 목적
(핵심 목표 + 달성 판단 기준. 시스템이 "어떻게" 가 아니라 "무엇을 가능하게 하는가" 로 서술)

## 주요 이해관계자
(직접/간접 이해관계자, 역할, 관심사 — 표 형식 권장)

## 주요 사항

> 이 섹션은 **무엇을 만들지가 아니라 누가 어떤 가치를 위해 사용하는지** 를 기술합니다.
> 기술 스택 / 컴포넌트 분할 / 통신 방식 / 데이터 모델 등 시스템 구조에 관한 결정은
> 후속 설계 단계(driver-select → style-define → design-decide) 의 책임입니다.

### 핵심 기능 요구사항 (User Story 관점)

- **[역할]로서**, [무엇을 할 수 있길 원하는지] — [왜/어떤 가치를 위해].
- (각 user story 는 한 단락. 시스템 구조 표현(컴포넌트명/프로토콜/DB명 등) 사용 금지)

### 핵심 품질 속성 (NFR)

| 속성 | 사용자 관점의 목표 |
|---|---|
| (예) 응답성 | (예) 에이전트 응답을 토큰 단위로 즉시 화면에서 확인할 수 있다 |

### 제약사항 (조직/정책/외부 환경)

- (조직 정책/규제/기존 자산 호환/벤더 종속 회피 등 — 기술 선택이 아니라 외부 제약만)
```

작성 후 사용자에게 **미리보기 제시** 후 수정 요청 받으면 반영.

### 작성 시 금지 사항 (재확인)

- ❌ "기술 스택", "확정 기술", "사용 라이브러리" 같은 절을 만들지 않는다.
- ❌ "핵심 아키텍처 결정", "컴포넌트 구성", "통신 방식" 같은 절을 만들지 않는다.
- ❌ user story 안에 특정 컴포넌트명/포트/프로토콜/DB명 박지 않는다 — "JIRA 양방향 동기화" 처럼 사용자가 인지하는 외부 시스템명은 OK, "Mongo 캐시", "SSE 스트리밍" 같은 내부 결정은 금지.
- ❌ 사용자가 답한 기술 선택을 그대로 기능 요구사항으로 옮기지 말 것 — 한 단계 위 가치로 재진술.

## Step 3 — 저장 (curl PUT)

확정된 마크다운을 `docs/{user}` 브랜치에 저장한다.

```bash
# 마크다운 본문을 /tmp/projdesc.md 에 저장했다고 가정 (에이전트가 Write 로 기록하거나 heredoc 사용)
cat /tmp/projdesc.md | bash "${PROJECT_ROOT}/.claude/skills/_scripts/doc-save.sh" "${CODE}" "${USER}" "business/project-description.md"
```

저장 응답(status/commit) 확인 후 사용자에게 경로/브랜치 보고.

## 주의

- **모든 쓰기 호출에 `X-User-Id: ${USER}` 헤더 필수**
- Platform-API 응답 content 는 **base64** → `| base64 -d`
- 저장 시에도 body.content 는 **base64 인코딩** 하여 전송
- 질문은 반드시 **한 번에 하나씩**, 채팅으로 자연스럽게. 다섯 개를 한 번에 쏟지 말 것.
- Self-loop 자가검증 없음 — 문서 품질은 사용자 확인으로 담보
- 한국어로만 대화

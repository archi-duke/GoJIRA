`docs/technical-decisions.md` 는 **주제별 색인**이고, `docs/decisions/YYYY-MM-DD-decisions.md` 가 **날짜별 원본**입니다. 이 스킬은 원본에서 색인으로 반영하는 일만 합니다 — **원본 로그는 고치지 않습니다.**

## 언제 호출하는가

**PR 단위 호출 (권장)** — PR 을 올리거나 머지할 때, 그 PR 이 기술 선택을 바꿨으면 호출합니다.
PR 하나가 결정 하나에 대응하는 경우가 많아 추적이 가장 정확합니다. 이때 `SINCE` 대신
`PR` 인자로 그 PR 만 봅니다.

```
Skill: decision-record     (PR=128)
```

판단 기준 — 아래에 하나라도 해당하면 기록 대상입니다.

- 쓰던 기술·라이브러리·방식을 **다른 것으로 바꿨다**
- 대안을 검토하고 **하나를 골랐다**
- 선택이 만든 **제약이나 함정**이 드러났다
- 이전 결정을 **번복했다**

반대로 버그 수정·리팩터링·의존성 갱신만 담은 PR 은 호출하지 않습니다.

**주기적 호출** — 여러 PR 이 누적된 뒤 한 번에 정리할 때는 `SINCE` 로 기간을 지정합니다.
이 경우 결정일을 PR 머지일로 역산해야 하므로 PR 단위보다 부정확합니다.

## 인자

- `PR` — (선택) PR 번호. 그 PR 의 커밋·본문·리뷰만 본다. **결정일은 머지일**(미머지면 오늘).
- `SINCE` — (선택) 이 날짜 이후를 본다. `PR` 과 함께 쓰지 않는다. 미지정 시 색인의 "갱신:" 날짜부터.
- `TOPIC` — (선택) 특정 주제만 갱신 (예: `런처`, `워크플로우`).

## 1. 현재 색인 상태 확인

```bash
cd "${PROJECT_ROOT:-.}"
head -5 docs/technical-decisions.md          # 갱신 날짜
grep -nE "^## |^### " docs/technical-decisions.md   # 주제·항목 구조
```

색인의 마지막 갱신 날짜를 `SINCE` 기본값으로 씁니다.

## 2. 새 재료 수집

`PR` 이 주어진 경우 — 그 PR 만 본다. 본문에 "왜" 가 적혀 있는 경우가 많아 가장 좋은 재료다.

```bash
gh pr view "${PR}" --json title,body,mergedAt,files,commits \
  --jq '{title, mergedAt, body, files: [.files[].path], commits: [.commits[].messageHeadline]}'
```

`mergedAt` 의 날짜(`[0:10]`)를 **결정일**로 쓴다. 미머지면 오늘 날짜를 쓰고, 머지 후 바뀌면 고친다.

`SINCE` 로 기간을 보는 경우:

```bash
# 날짜별 로그 — 색인에 아직 없는 것
ls docs/decisions/*.md
for f in docs/decisions/*.md; do echo "[$(basename $f)]"; grep -E "^## " "$f"; done

# 기술 전환·폐기 커밋
git log --since="${SINCE}" --format="%ad %h %s" --date=format:"%Y-%m-%d" \
  | grep -iE "폐기|제거|전환|교체|대체|이관|분리|revert|pivot|refactor"

# 설계서 변경 (결정이 반영된 흔적)
git log --since="${SINCE}" --format="%h %s" -- docs/design-*.md docs/decisions/
```

## 3. 반영할 것을 가린다

색인에 넣는 것은 **기술 선택과 그 변경**입니다. 아래는 넣지 않습니다.

- 단순 버그 수정, 오타, 포맷
- 구현 세부(함수 이름, 파라미터)
- 일회성 운영 조치

반대로 **반드시 넣어야 하는 것**:

- 기술·라이브러리·아키텍처 선택과 그 이유
- **폐기한 대안과 폐기 이유** — 이게 색인의 핵심 가치다
- 선택의 대가(trade-off), 특히 나중에 문제가 된 것
- 운영에서 드러난 함정 (다음 사람이 같은 데 빠지지 않게)

## 4. 항목 형식

주제 아래에 `###` 로 넣고, 아래 순서를 지킵니다. 모든 줄이 필수는 아니되 **선택·이유는 반드시** 적습니다.

```markdown
### <결정 한 줄 — 무엇을 택했나>

**결정일**: YYYY-MM-DD

**선택**: 무엇을 어떻게 하기로 했는지.
**이유**: 왜 그게 나은지. 대안과 비교해서.
**폐기한 것**: 이전에 쓰던 것 (있을 때만).
**왜 바꿨나**: 폐기 이유. 구체적 증상이 있으면 그것을.
**대가**: 이 선택이 만든 제약 (있을 때만).
**주의** / **운영 주의**: 다음 사람이 빠질 함정 (있을 때만).
**참조**: `decisions/YYYY-MM-DD` D번호 · 설계서 · PR·커밋 번호.
```

## 5. 작성 원칙

- **결정일을 반드시 적는다.** 출처 우선순위는 ① `decisions/` 파일명 ② PR 머지일 ③ 커밋일 ④ 설계서 갱신일.
  범위로만 아는 것은 `2026-04-22 ~ 04-29` 처럼, 끝내 모르면 `미확인` 으로 적고 추정하지 않는다.
  **번복된 결정은 두 날짜가 모두 보이게** 한다 — 언제 정하고 언제 바꿨는지가 이력의 핵심이다.
- **참조를 반드시 단다.** 색인은 요약이므로, 원본을 찾아갈 수 있어야 한다. 원본과 어긋나면 원본이 정본.
- **폐기된 결정을 지우지 않는다.** 왜 폐기했는지가 다음 판단의 재료다. 번복된 결정은 두 항목으로 남기거나 한 항목에 경위를 적는다.
- **수치가 있으면 넣는다.** "빨라졌다" 보다 "5분 9초 → 9초" 가 판단에 쓰인다.
- **확인되지 않은 것은 단정하지 않는다.** 추정이면 추정이라고 적는다.
- 분량은 항목당 3~6줄. 전체가 너무 길어지면 주제를 나누지 말고 **오래된 항목을 압축**한다.

## 6. 반복되는 교훈 갱신

문서 끝의 "반복되는 교훈" 은 **여러 사고에서 같은 형태로 되돌아온 것**만 적습니다. 새 결정 하나로는 추가하지 않고, 기존 교훈에 사례가 하나 더 붙었으면 그 항목에 보탭니다.

## 7. 마무리

```bash
head -5 docs/technical-decisions.md   # 갱신 날짜를 오늘로 수정했는지 확인
git diff --stat docs/technical-decisions.md
```

- 문서 머리의 `**갱신**:` 날짜를 오늘로 바꾼다.
- 커밋은 하지 않는다. 사용자에게 변경 요약(추가한 항목 수, 주제)을 한국어로 보고하고 커밋 여부를 묻는다.

## 결과 보고

반영한 항목을 주제별로 나열하고, **판단이 필요한 것**을 따로 적습니다.

- 새 결정이 기존 항목과 충돌하면 어느 쪽이 유효한지 사용자에게 묻는다.
- 날짜별 로그에 미결(`미결:`, `보류`)로 남은 것은 색인에 넣지 않고 "미결 상태" 로만 보고한다.

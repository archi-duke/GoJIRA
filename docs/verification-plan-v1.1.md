# 검증 실험 작업 지시서 — v1.1 개정안

**대상**: 사외 환경에서 실험을 수행하는 AI Agent(및 담당자)
**목적**: AI 기반 설계 지원 플랫폼에 채택한 설계 패턴 7종의 **설계 타당성**을 공개 데이터셋 · 공개 OSS · 기존 운영 실측으로 확인한다.
**버전**: v1.1 (2026-11-14) — v1.0(2026-11-12) 개정

## 개정 요약

v1.0 은 각 실험에 운영 목표치(p95 ≤ 5s, F1 ≥ 0.8, pass^k ≥ 0.9 …)를 두어, 실질적으로 **운영 환경 재현**에 가까운 작업량을 요구했다. v1.1 은 목적을 다음으로 좁힌다.

> **이 설계 선택이 대안보다 나은가, 그리고 그 우위가 공개 데이터 또는 기존 운영 실측에서 재현되는가.**

이 질문은 **비교군 간 상대 차이**로 답할 수 있다. 절대 목표치·운영 규모·대규모 반복은 "운영 보증" 영역이므로 설계 판단에서 제외한다.

여기에 **구현 수준에 따라 검증 성격을 나눈다**는 방침을 더한다.

| 구현 상태 | 검증 성격 |
|---|---|
| 이미 구현되어 운영 중 | **운영 실측 결과를 제시**한다. 새 실험보다 직접적이다 |
| 부분 구현 | 미구현 부분만 소규모 실측 |
| 미구현 (설계 제안 단계) | **설계 타당성을 입증하는 외부 검증을 참조**한다 |

## 0. 이 문서를 읽는 방법

- 이 문서만으로 작업을 시작할 수 있게 썼다. 이 문서에 없는 내부 자료는 존재하지 않는 것으로 간주하고, 요청하지도 추측하지도 않는다.
- 실험은 E1~E7 로 나뉜다. 각 실험은 독립적으로 수행할 수 있다. 권장 순서는 7장을 따른다.
- 모든 실험은 **측정 정의를 먼저 확정(사전 등록)** 한 뒤 실행한다. 실행 후 정의를 바꾸지 않는다.
- **판단 기준**: 각 실험이 답해야 하는 것은 "목표치를 넘었는가"가 아니라 **"이 설계 선택이 대안보다 나은가"** 다. 비교군 간 차이를 1차 지표로 보고하고, 절대 목표치는 참고치로 적는다.
- **근거의 성격을 구분한다**: ① 기존 운영 실측 ② 이 실험의 공개 재현 ③ 외부 공개 연구 인용. 보고서에 어느 것인지 반드시 표시한다.

## 4. 실험별 상세

### E1. 2단계 검색 — 대부분 인용, 오버헤드만 실측

**가설**: ANN 으로 후보 top-100 을 먼저 뽑고 정밀 재계산으로 top-5 를 고르면, 정확도 손실을 작게 유지하면서 검색 지연을 늘리지 않는다.

**인용으로 대체하는 부분**
- ANN 단계의 규모별 지연·Recall 곡선은 [ann-benchmarks](https://ann-benchmarks.com) 가 GloVe-100 · SIFT-1M · DEEP 계열에 대해 HNSW / IVF-PQ 로 이미 공표한다. 재측정해도 같은 곡선이 나온다.
- "ANN top-100 → Flat 재계산 top-5" 의 Recall@5 는 **ANN 의 Recall@100 으로 환원**된다. ANN 의 Recall@100 은 Recall@10 보다 항상 높으므로, "정확도 손실을 작게 유지" 는 측정 전에 성립한다.

**직접 측정하는 부분 (반나절)**
- **2단계가 더하는 오버헤드만** FAISS 로 1M 규모에서 1회 측정한다. 재계산 후보는 top-100 고정이므로 이 비용은 N 과 무관하다는 것을 한 점으로 보인다.
- 조건: 벡터 **1M** (10M·DEEP 제외), 동시 질의 **1 · 10 · 50**. 운영에서 p95 를 밀어올리는 것은 데이터 규모보다 동시성이다.
- 선택: 중간 규모 **3M** 한 점을 더하면 지연-규모 기울기가 나와 외삽 근거가 된다 (SIFT-1M 을 쌓거나 DEEP 부분집합 사용, 32 GB 내 가능).

**지표 — 재랭크와 Flat 재계산을 분리한다 (v1.0 오류 수정)**
- Flat 재계산: Recall@5, 정답은 brute-force 결과.
- Cross-Encoder 재랭크: **brute-force 를 정답으로 쓰지 않는다.** 재랭커의 목표 함수가 다르므로 BEIR 등 **관련성 라벨** 기준으로 평가하거나, 이 변형을 E1 에서 제외한다.
- 단계별·합계 지연 p50 / p95 / p99 (질의 임베딩 포함, LLM 응답 생성 제외).

**산출물**: `e1_latency.csv`, 지연-Recall 곡선 PNG, 인용 수치는 `CITATIONS.md` 에 출처 명기.

### E2. Chunking 방식 비교 — 인용으로 대체

**가설**: 문서 구조를 반영한 Chunking 이 고정 크기 Chunking 보다 검색 품질이 높다.

**인용**: [Chroma — Evaluating Chunking Strategies for Retrieval](https://research.trychroma.com/evaluating-chunking) 가 v1.0 이 지정한 `chunking_evaluation` 프레임워크의 **원 보고서**다. splitter 간 Recall 차이는 작고(공표치 기준 86.7~91.7%), **토큰 단위 Precision 은 1.5~8%** 로 낮으며 splitter 간 편차는 Precision 에서 더 크다.

> **사전 등록 전 필수 확인**: 위 수치는 2차 출처에서 가져온 것이고 출처 간 불일치가 있다. 1차 보고서의 표를 직접 대조하고 `CITATIONS.md` 에 표 번호까지 적는다.

**v1.0 의 `F1 ≥ 0.8` 목표치를 삭제한다 — 이 지표 정의로는 달성 불가능하다**

```
토큰 단위 Precision 4~8%   (청크 200~800 토큰 vs 정답 발췌 수십 토큰 — 구조적)
Recall ≈ 90%
→ F1 ≈ 0.1
```

F1 ≥ 0.8 이 나오려면 Precision 70% 이상이 필요하나 구조적으로 불가능하다. 그대로 측정하면 "미충족" 결과가 나오고, 그것이 설계 반박으로 오독될 위험이 있다. **설계가 틀린 것이 아니라 측정 정의가 잘못 이식된 것이다.**

**교체 지표**: `Recall@5` 와 `IoU` 의 **(Fixed Size 대비) 상대 개선폭**. 절대 목표치는 두지 않는다.

**비교군에서 Parent-Child 를 제외한다**: Parent-Child 는 chunking 방식이 아니라 **검색 시점의 small-to-big 치환** 기법이므로 `chunking_evaluation` 프레임워크 안에 없다. 넣으려면 평가 루프를 수정해야 하므로 범위를 벗어난다. 남는 비교군은 **Fixed Size vs Context Aware(Semantic)**.

**직접 돌리는 경우 (선택, 1일)**: 임베딩을 bge-m3 로 바꾼 조건만 재현한다. 원 연구와 다른 점을 보고서에 명시한다.

### E3. GraphRAG vs Hybrid vs Query Router

**가설**: 그래프 기반 검색은 Multi-Hop 질의의 정확도를 높이지만 지연이 늘어난다. 그래프가 필요 없는 질의를 벡터 경로로 보내는 Router 를 두면 지연을 줄일 수 있다.

**(a)(b) 는 인용한다**: [HippoRAG 2 (arXiv 2502.14802)](https://arxiv.org/abs/2502.14802) Table 3 이 HotpotQA · 2Wiki · MuSiQue 에 대해 passage Recall@5 를 BM25 / Contriever / LightRAG / HippoRAG / HippoRAG 2 로 공표한다. 여기서 설계 판단에 필요한 결론이 나온다.

- 그래프 검색의 이득은 **데이터셋의 Multi-hop 구조에 따라 0~20pt 로 크게 다르다** (HotpotQA 에서는 BM25 와 동급).
- **어느 GraphRAG OSS 를 택하느냐가 결과를 지배한다.** 같은 범주라도 LightRAG 는 Recall@5 가 한 자릿수다. v1.0 의 "MS GraphRAG / LightRAG / HippoRAG 중 1종 이상" 은 너무 느슨하다 — 사전 등록 시 **구조가 가장 가까운 것 하나를 명시**한다.

> **인용 시 명시할 간극**: HippoRAG 는 PPR(Personalized PageRank) 기반이고, 검증 대상 설계는 LLM 이 Cypher 를 생성해 그래프를 질의하는 방식이다. 구조가 다르므로 "그래프 검색 일반의 이득" 까지만 인용하고, 특정 구현의 수치를 그대로 가져오지 않는다.

**(c) Router 만 직접 측정한다 (1주)**

Router 는 공개 비교가 없고, 검증 대상 시스템에도 **아직 구현되지 않은 설계 제안**이다. 7종 중 가장 검증 가치가 높다.

- 만들 것: 질의 분류기 1개(휴리스틱 또는 LLM 1회 호출, 100~200줄) + 두 경로 디스패처 + 200문항 러너. 그래프 구축은 공개 OSS 에 맡긴다.
- 데이터: HotpotQA dev-distractor · 2WikiMultihopQA · MuSiQue-Ans 에서 200문항 (단일 Hop 100 / Multi-Hop 100). 멀티홉 라벨은 데이터셋이 제공한다.
- 측정: ① Router 분류 정확도 ② 벡터 경로로 보낸 질의의 Recall@5 손실 ③ 평균·p95 지연 감소.
- **삭제**: 1× / 5× 규모 조건, 5회 반복 동일 응답률 (운영 안정성 지표이며 Router 판단에 불필요).

**분류기 없이 상한만 보는 길**: 라벨된 단일/멀티홉 질의에 대해 벡터 경로와 그래프 경로의 정확도를 각각 재면 Router 의 **이론적 상한**이 나온다. "Router 가 가치 있는 영역이 존재하는가" 는 이것만으로도 답할 수 있다.

**산출물**: `e3_router.csv`, 경로별 비교 그래프. 그래프 구축 비용·시간 별도 기록.

### E4. 근거(Evidence) 필드의 효과 — 소규모 파일럿

**가설**: 지식을 (주어, 관계, 목적어)에 근거를 더한 4요소로 저장하면, 응답이 실제 근거를 더 정확히 가리킨다.

**규모 축소**: v1.0 의 100문항 × 3회 → **30~50문항 × 1회**.

이 설계는 "근거 포인터를 저장해 두고 돌려주는 것 vs 사후에 재구성하는 것" 이므로 **개선 방향은 거의 논리적 필연**이다. 실험이 답해야 할 것은 개선폭의 크기가 아니라 **"사후 인용이 예상보다 잘 되어서 4요소가 불필요한가" 라는 반증 가능성**이다. 소규모로 충분하다.

**지표 단위를 설계에 맞춘다**: v1.0 은 문장 단위 IoU 를 요구했으나, 검증 대상 설계의 근거는 **청크 단위**다. 설계보다 세밀한 지표로 재면 설계가 하지 않는 일을 평가하게 된다. → **청크 단위 IoU** 로 바꾸고, 문장 단위는 선택으로 둔다.

- 데이터: E3 의 200문항 중 30~50문항. HotpotQA supporting facts 를 정답 근거로 쓰므로 사람 라벨링은 없다.
- 비교군: (a) 3요소 + 사후 인용 생성 (b) 4요소(근거 포함).
- 보고: 절대값보다 **(a) 대비 개선폭**을 중심으로. 문장 단위 IoU 는 토큰 단위보다 높게 나오는 경향이 있으므로 단위를 반드시 명시한다.

**산출물**: `e4_iou.csv`.

### E5. Non-determinism 격리와 Guard Rail 준수 — 축소

**가설**: Workflow 상태 전이를 코드(State Machine)로 고정하고 LLM 은 상태 단위 작업만 하게 하면, Prompt 만으로 통제할 때보다 반복 실행 시 규칙 준수가 안정된다. 외부 Critique 를 더하면 더 좋아진다.

**기준선은 인용한다**: [τ-bench (arXiv 2406.12045)](https://arxiv.org/abs/2406.12045) 가 (a) Prompt Harness 의 공개 기준선을 제공한다 — GPT-4o retail pass^1 ≈ 61%, **pass^8 ≈ 25%**. "반복 시 규칙 준수가 무너진다" 는 문제 정의 자체는 측정 없이 인용 가능하다. (airline 수치는 미확인.)

**규모 축소 (비용 $450 → $120~180)**

| | v1.0 | v1.1 |
|---|---|---|
| k | 1, 4, 8 | **4** (감쇠 곡선 형태는 공개 논문이 제공. 필요한 것은 비교군 간 간격) |
| 비교군 | (a)(b)(c) 3군 | **(a)(b) 2군 먼저** → (b) > (a) 확인 후 (c) 추가 |
| 시행 | 20과제 × 8 × 3군 = 480 | 20 × 4 × 2 = **160** (+조건부 80) |

**지표 — 절대치를 참고치로 격하한다**

v1.0 의 `pass^k ≥ 0.9` 는 공개 기준선(pass^8 ≈ 25%) 대비 비현실적이다. 설계 판단에 필요한 것은 **(a) 와 (b) 의 간격**이다.

- 1차 지표: **준수 pass^4 의 (a)-(b) 간격**. 성공 pass^4(τ-bench 원 정의, 최종 상태 일치)는 함께 보고하되 분리한다.
- 정책 위반 판정기는 **기계 판정 가능한 규칙 5~8개로 한정**해 사전 등록한다 (예: "조치 전 확인 발화 존재", "환불 조건 불충족 시 도구 호출 없음"). 정책 문서 전체를 코드화하는 것은 운영 보증 영역이다.
- User Simulator 는 저가 모델 사용 가능 (보고서에 명시).

**만들 것**: ① τ-bench 20과제용 State Machine 하네스(LangGraph 사용 시 500~800줄) ② Critic 호출 + 재작업 루프(200줄) ③ 정책 위반 판정기(300~600줄 + 사전 등록 문서) ④ 반복 실행 하네스(E6 와 공유).

> **공개 수치 공백**: "코드 State Machine 이 Prompt-only 보다 규칙 준수를 안정화한다" 는 비교의 공개 논문 수치는 찾지 못했다. 이것이 E5 (b) 를 직접 측정해야 하는 이유다. 다만 폭넓게 조사하지는 않았으므로, 착수 전 한 번 더 문헌을 확인한다.

**산출물**: `e5_passk.csv`, (a)-(b) 간격 그래프, 판정기 코드와 규칙 목록(사외 보관).

### E6. 절차 기반 Agent Workflow + Skills

**가설**: 작업 절차를 단계와 Skill 로 고정한 Agent Workflow 는, 역할만 부여한 Multi-Agent 보다 같은 입력에 대해 같은 결과를 더 자주 낸다.

**데모 신규 구현이 불가피하다**: 검증 대상 시스템에 이 패턴의 동작 구현체가 있으나, 1장 규칙(내부 코드 사용 금지)과 충돌하고 내부 API 에 결합되어 사외로 분리할 수도 없다. → 공개 데모를 새로 만든다.

- 데모: "요구사항 문서 → 기능 목록 → 요구사항 정제 → 우선순위 선정" 3단계 Workflow.
- 규모 감각: SKILL.md 3종(각 200~300줄) + validator 3종(각 200~300줄) + 결정적 조립 1종 + 판정기 ≈ **1,500~2,000줄**. 비교군 CrewAI/AutoGen 은 수백 줄.
- 입력: 공개 SW 요구사항 문서 셋(PURE 등, 라이선스 확인) 또는 공개 OSS 의 README·Issue.

**판정 기준 완화**

v1.0 의 "구조 Jaccard ≥ 0.9 **AND** 의미 cosine ≥ 0.9 동시 만족" 은 LLM 도출 단계에 과도하다. 경험상 **문서 조립은 결정적이어서 재현율이 구조적으로 보장되지만, 도출 단계는 LLM 이라 항목 수·명명이 흔들린다.**

- 1차 지표: **(a) 와 (b) 의 동일 응답률 차이.** 0.9 절대치는 참고치.
- **단계별로 분리 보고한다** — 결정적 조립 단계와 LLM 도출 단계를 섞으면 설계 효과가 가려진다.
- `Error Rate ≤ 1%` 삭제: 90회 표본에서 0 또는 1건을 뜻해 비율이 무의미하다. → **건수와 원인 분류로 보고**한다.
- 규모: 입력 3종 × 단계 3 × 10회 = 90회 + 비교군 45회 (v1.0 과 동일).

**산출물**: `e6_consistency.csv`, 판정기 코드(사외 보관), 단계별 분리 표.

### E7. 협업 기록 기반 Trajectory 재구성 — 대폭 축소

**가설**: Agent 와 사람의 작업을 공통 스키마로 기록하면, 결함이 생겼을 때 원인 단계를 빠르게 찾을 수 있다.

**전제는 인용한다**: [Who&When (arXiv 2505.00212)](https://arxiv.org/abs/2505.00212) 가 이미 답을 준다 — 최고 방법도 **원인 에이전트 식별 53.5%, 원인 단계 식별 14.2%**, 수작업 시스템에서는 단계 정확도 10% 미만. "구조화되지 않은 로그에서 원인 단계를 찾는 것은 매우 어렵다" 는 가설의 전제가 공개 수치로 성립한다. **v1.0 의 "Who&When 으로 지표 선행 검증" 단계는 돌리지 말고 인용한다.**

**삭제하는 것**

| 항목 | 이유 |
|---|---|
| Mattermost / Matrix + Agent Hook 구축 | **운영 환경 구축**이며 설계 검증이 아니다. 설계의 핵심은 공통 스키마의 효과이고, 메신저 없이 **JSONL 레코드**로 동일하게 측정된다 |
| OpenTelemetry + Langfuse | 같음 |
| **재구성율 ≥ 95%** | 스키마에 `parentId`·`step` 이 있으면 복원은 결정적이라 **구조적으로 100%** 가 나온다. 떨어지는 경우는 Hook 이 메시지를 놓친 것이므로 **구현 신뢰성 측정**이지 설계 측정이 아니다 |
| Orchestrator 교체 0 / 1 / 3회 | 운영 시나리오 |
| LLM 평가자 1차 사용 | Who&When 상 LLM 의 단계 귀인 정확도가 8~14% 다. **사람 평가자를 기준**으로 하고 LLM 은 보조로 둔다 |

**남기는 최소 실험 (1주)**

E6 데모의 실행 로그에 결함을 1개씩 주입한 20건을 두 형태로 준비해 비교한다.

```
① 공통 스키마 적용 기록   agentId · parentId · step · input/output hash · timestamp
② 평문 로그 (스키마 없음)
→ 사람 평가자 2명이 원인 단계를 찾는 시간·정답률을 비교
```

이것이 설계 주장("기록 구조가 원인 식별을 빠르게 한다")에 직결되는 유일한 비교다. 주입 단계는 정답으로 따로 기록한다.

**만들 것**: 레코드 writer + 결함 주입 스크립트 200~300줄. 결함 유형은 v1.0 과 동일 (잘못된 입력, 규칙 위반, 중간 산출물 변조).

**산출물**: `e7_attribution.csv`, 기록 스키마 문서.

## 5. 산출물 형식

실험마다 `reports/E{n}_report.md` 를 아래 형식으로 작성한다.

```
# E{n} <실험명>
1. 가설
2. 측정 정의 (사전 등록 내용 그대로, 변경 없음 확인)
3. 근거의 성격          ← v1.1 추가
   ① 기존 운영 실측 / ② 이 실험의 공개 재현 / ③ 외부 공개 연구 인용
   각 결론이 어느 것에 근거하는지 표시
4. 환경 (모델·버전, OSS·버전·commit, 하드웨어)
5. 데이터 (출처, 라이선스, 샘플 수, 샘플 ID 목록 위치)
6. 결과 표 (비교군별 평균·p95·표준편차·반복 수)
7. 비교군 간 차이와 그 해석   ← v1.1: 1차 지표
8. 목표 대비 참고 (충족 / 미충족 / 판정 불가 + 이유)   ← v1.1: 참고치로 격하
9. 한계 (공개 데이터 기준이라 일반화가 어려운 점, 원 정의와 다른 점, 외삽하지 않은 범위)
10. 비용·시간 실적
11. 제외한 실행과 사유
```

**결과 표기 규칙**

- 모든 수치에 **"공개 데이터셋 기준 사외 실측"** 또는 **"외부 연구 인용 (출처)"** 를 함께 적는다.
- **"설계 패턴 검증"과 "시스템 실측"을 구분한다.** 이 실험의 결과는 모두 설계 패턴 검증이다.
- 목표값을 충족하더라도 "실제 시스템이 목표를 충족한다"고 쓰지 않는다. **"같은 패턴으로 목표 충족 가능성을 확인했다"** 까지만 쓴다.
- 인용 수치는 `CITATIONS.md` 에 출처·버전·표 번호를 적고, 2차 출처는 1차 대조 여부를 명시한다.
- 외삽하지 않은 범위를 한계에 적는다 (예: "1M 기준이며 그 이상 규모는 확인하지 않았다").

## 7. 권장 순서

**인용으로 끝나는 것을 먼저 처리해 틀을 잡는다.**

1. **E2 → E1** (0~2일): 인용 중심. 지표 정의·공통 러너·`CITATIONS.md` 형식을 여기서 확정한다. E1 의 오버헤드 측정만 짧게 돌린다.
2. **E3 (a)(b) 인용 → E3 (c) Router 실측** (1주): 평가셋과 환경을 E4 와 공유한다.
3. **E4** (2~3일): E3 의 평가셋 재사용.
4. **E5 와 E6 병렬** (2주): 반복 실행 하네스(초기화 → 실행 → 판정 → 기록)를 공유하면 준비 시간이 줄어든다. E6 의 데모 산출물은 E7 입력으로 재사용한다.
5. **E7** (1주): E6 산출물에 결함을 주입해 사람 평가로 비교.

예상 기간 **1인 순차 5~7주, 2인 병렬 3~4주**.

## 부록. v1.0 에서 발견된 측정 정의 오류

사전 등록 전에 반드시 반영해야 하는 것들이다. v1.0 그대로 실행하면 설계가 타당한데도 "미충족" 결과가 나올 수 있다.

| 정의 | 문제 | 조치 |
|---|---|---|
| E2 `F1 ≥ 0.8` (토큰 단위) | 프레임워크 지표 정의상 **달성 불가능** (Precision 4~8% → F1 ≈ 0.1) | 상대 개선폭으로 교체, 목표치 삭제 |
| E1 `Recall@5` 정답 = brute-force | Cross-Encoder 재랭크에는 **잘못된 기준** (목표 함수가 다름) | Flat 재계산과 재랭크를 분리 평가 |
| E5 `pass^k ≥ 0.9`, k=8 | 공개 기준선 pass^8 ≈ 25% 대비 비현실적. 480 시행 | k=4, (a)-(b) 간격을 1차 지표 |
| E6 `Jaccard ≥ 0.9` AND `cosine ≥ 0.9` | LLM 도출 단계에 과도. 결정적 조립 단계는 자동 100% | 차이를 1차 지표, 단계별 분리 보고 |
| E6 `Error Rate ≤ 1%` | 90회 표본에서 0 또는 1건 — 비율 무의미 | 건수와 원인 분류로 보고 |
| E7 `재구성율 ≥ 95%` | 스키마 설계상 결정적 → **구현 신뢰성 측정** | 삭제 |
| E7 원인 식별 ≤ 10분 (LLM 평가자) | Who&When 상 LLM 단계 귀인 8~14% | 사람 평가자 기준 |
| E4 문장 단위 IoU | 검증 대상 설계는 **청크 단위** 근거 | 설계 단위에 맞춤 |
| E2 Parent-Child 비교군 | chunking 이 아니라 **검색 시 치환** 기법. 프레임워크 밖 | 제외 |
| E3 "GraphRAG OSS 중 1종 이상" | 어느 것을 택하느냐가 **결과를 지배** (LightRAG Recall@5 는 한 자릿수) | 사전 등록에 1종 명시 |

# Project Description — GoJIRA

> 본 문서는 GoJIRA 자체 프로젝트(플랫폼 개발 과제)의 설명입니다.
> GoJIRA 가 관리하는 사용자 프로젝트별 `business/project-description.md` 와는 별개입니다.

## 과제 배경

JIRA Datacenter 는 사내 표준 이슈 관리 도구로 자리 잡았으나, SW/시스템 엔지니어링 프로젝트 운영 측면에서 다음 한계가 누적적으로 드러났습니다.

- **이슈 ↔ 설계 문서 단절**: JIRA 의 이슈와 별도 위키/공유 드라이브의 설계 문서가 분리되어 있어, 변경 추적과 일관성 유지가 수동·인력 의존적입니다.
- **요구사항 → 아키텍처 → 설계 단계의 추적성 부재**: VOS(이해관계자 요구) → Use Case/Feature → Requirement(FR/NFR/CNST) → Architecture Driver → Style/Design 의 흐름을 일관되게 추적하는 도구가 없어, 결정 근거가 휘발됩니다.
- **반복적 산출물의 수작업 부담**: 문서 초안 작성, 다이어그램(PlantUML) 작성, QA 가중 평가 등 정형화 가능한 작업이 매번 사람의 시간을 먹습니다.
- **외부 SaaS LLM 직접 사용의 정책적 제약**: 사내 보안 정책상 OpenAI/Anthropic 등 외부 LLM 을 클라이언트가 직접 호출하는 구조는 채택이 어렵습니다. 키 관리·감사·게이트웨이 통제가 가능한 자체 인프라가 요구됩니다.
- **단일 LLM 벤더 런타임 종속의 위험**: Claude Agent SDK 등 단일 벤더 런타임을 채택하면 모델 교체·장애·정책 변경에 취약해집니다. 모델 중립적 실행 환경이 필요합니다.

## 과제 목적

**JIRA Datacenter 호환 이슈 관리 + Git 기반 설계 문서 + AI 에이전트 워크플로우 자동화** 를 단일 인터페이스로 제공하는 자체 호스팅 플랫폼을 구축합니다.

핵심 가치는 다음 세 가지입니다.

1. **Single Pane of Glass**: 이슈, 설계 문서, AI 에이전트 대화, 진행 현황 알림을 하나의 SPA 에서 다룹니다.
2. **Traceable Design Workflow**: VOS → Feature → Requirement → Driver → Style/Design 까지 이슈 링크 + Git 커밋으로 결정 근거를 영구 보존하고, 변경 영향(drift) 을 자동 감지합니다.
3. **Skill-Driven AI 자동화**: 자연어 요청을 받아 선언형 스킬(`SKILL.md`) 을 디스패치하는 에이전트로, 워크플로우 단계별 산출물을 LLM + 결정적 도구 조합으로 자동 생성합니다.

데이터·LLM 키·문서는 모두 자체 인프라(MongoDB, Gitea, 사내 LLM 게이트웨이) 에 보관되며, 외부 의존성은 정책 통제 가능한 단일 게이트웨이를 통해서만 발생합니다.

| **아키텍트** | 워크플로우 산출물 검수자 | Driver→Style→Design 추적성, ADSN/DDSN 결정 근거, SATAM 매트릭스 |

## 주요 사항

> 이 섹션은 **무엇을 만들지가 아니라 누가 어떤 가치를 위해 사용하는지** 를 기술합니다.
> 기술 스택 / 컴포넌트 분할 / 통신 방식 / 데이터 모델 등 **시스템 구조에 관한 결정은
> 후속 설계 단계(driver-select → style-define → design-decide)** 의 책임입니다.

### 핵심 기능 요구사항 (User Story 관점)

- **엔지니어로서**, 사내 표준 JIRA 에 이미 누적된 이슈 이력을 그대로 유지하면서 새 도구
  안에서 조회/편집할 수 있어야 한다 — 기존 자산을 폐기하거나 마이그레이션할 수 없는
  조직 현실 때문에.
- **엔지니어/아키텍트로서**, 설계 문서를 코드처럼 버전 관리하고 동료 리뷰를 거친 뒤
  본문에 반영하길 원한다 — 현재 위키/공유드라이브의 변경 추적 부재와 회의록 같은
  부수 자료에 결정 근거가 휘발되는 문제를 해소하기 위해.
- **아키텍트로서**, 이해관계자 요구(VOS) 부터 최종 설계 결정(ADSN/DDSN) 까지 추적 가능한
  체인을 유지하고, 상위 요구가 바뀌었을 때 영향받는 하위 산출물을 자동으로 파악하길
  원한다 — 결정의 근거 손실과 silent drift 를 막기 위해.
- **엔지니어로서**, 정형화 가능한 산출물(요구사항 정제, 유즈케이스 분석, 다이어그램, QA
  평가 등) 을 자연어로 요청해 초안을 자동 생성받기를 원한다 — 매번 처음부터 작성하는
  반복 비용을 줄이기 위해.
- **엔지니어/PM 으로서**, 에이전트의 응답을 기다리는 동안 진행 상황을 즉시 보고 동료의
  공지/알람을 실시간으로 받기를 원한다 — 자동화 작업이 길어질 때 멈춘 듯한 UX 가 신뢰를
  떨어뜨리기 때문에.
- **사용자로서**, 사내 SSO 로 한 번 로그인한 뒤 부여된 권한 내에서만 작업이 가능해야
  한다 — 별도 계정/패스워드 운영 부담 없이 사내 감사 정책을 충족하기 위해.
- **PM 으로서**, 프로젝트의 진행률/일정 지연 리스크를 시각적으로 파악하고 양방향
  JIRA 동기화 상태를 확인할 수 있어야 한다.

### 핵심 품질 속성 (NFR)

| 속성 | 사용자 관점의 목표 |
|---|---|
| 데이터 주권 | 모든 이슈/문서/세션 데이터가 외부 SaaS 가 아닌 조직 내부에 보관됨이 보장된다 |
| 시크릿 보안 | 평문 API 키·패스워드가 .env / git / 로그 어디에도 남지 않는다 |
| LLM 통제 가능성 | LLM 호출에 대해 키 회수·감사 로그·요청 차단·rate limit 을 단일 지점에서 적용할 수 있다 |
| 실시간성 | 에이전트 응답을 토큰 단위로 즉시 화면에서 확인할 수 있다 |
| 다이어그램 정확성 | LLM 출력의 흔한 다이어그램 문법 오류로 인한 렌더 실패가 사용자에게 노출되지 않는다 |
| 자동화 산출물 품질 | 자동 생성된 산출물이 사람의 추가 보정 없이도 다음 단계의 입력으로 사용 가능한 수준이다 |

### 제약사항 (조직/정책/외부 환경)

- **사내 보안 정책**: 외부 SaaS LLM 을 클라이언트가 직접 호출하는 구조는 채택 불가.
  반드시 정책 통제가 가능한 단일 게이트웨이를 통과해야 한다.
- **벤더 종속 회피 정책**: 특정 LLM 벤더의 폐쇄적 런타임에 종속되는 구조는 모델 교체·
  장애·정책 변경에 취약하므로 채택 불가.
- **JIRA Datacenter 호환 필수**: 사내 표준이 JIRA DC 이므로 v2 REST 호환 범위 내에서만
  동작해야 하며, JIRA Cloud 전용 기능은 가정 불가.
- **자체 호스팅 전제**: SaaS 형태 배포는 고려 대상이 아니다. 모든 의존 인프라(이슈 저장소,
  문서 저장소, LLM 게이트웨이 등) 는 사내 운영 가능해야 한다.
- **사내 인증 체계**: 사용자 인증은 사내 SSO(ADFS) 를 사용한다 — 자체 계정 체계는 가정 불가.

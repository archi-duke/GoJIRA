
[기본 원칙]
- Git 플랫폼은 용도에 따라 분리하여 사용한다.
  - 소스코드 저장소: GitHub
  - 설계문서 저장소: Gitea (self-hosted, Docker 기반)
- 설계문서를 Gitea에서 관리하는 이유:
  - 설계서의 보안성 확보 (private 레포에서도 branch protection 무료 지원)
  - GitHub Free 플랜의 private 레포 제약 회피 (branch protection 미지원)
  - self-hosted 환경으로 데이터 주권 확보
- Gitea는 GitHub REST API 호환 구조(API v1)를 제공하므로, 기존 GitHub 연동 코드를 최소 변경으로 재사용한다.
- 사용자는 Git 플랫폼에 직접 익숙하지 않아도 되도록, 과제 중심의 간편한 UI를 별도로 제공한다.
- 문서는 Markdown 기반이며, 여러 파일로 구성된 계층형(hierarchy) 구조를 가진다.
- 문서와 소스코드는 연결 관리되어야 한다.
- 승인자는 Project의 auditors 필드에 등록된 사용자로 한다.
- auditors 정보가 없으면 승인 기능을 진행하지 말고, 먼저 auditor를 지정하라는 안내를 제공한다.

[구현 목표]
다음 요구사항을 만족하는 시스템 또는 모듈을 설계하고 구현하라.

1. Git 플랫폼 사용
- 설계문서 저장소와 형상관리는 Gitea(self-hosted)를 사용한다.
- 소스코드 저장소는 GitHub를 유지한다.
- 문서 변경은 Git commit, branch, PR 기반으로 관리한다.
- Gitea API(v1)를 활용할 수 있도록 구조를 설계하며, GitHub API 호환성을 유지한다.
- 환경 설정(GITHUB_URL)만 변경하면 GitHub ↔ Gitea 전환이 가능하도록 설계한다.

2. 프로젝트 설계서용 레포지토리 생성
- 과제 또는 프로젝트에 대해 설계서용 GitHub repository를 생성할 수 있어야 한다.
- 단, 사용자 또는 요청자의 권한 코드가 GITRP 15 이상인 경우에만 repository 생성이 가능해야 한다.
- 권한 조건을 만족하지 않으면 repository 생성 기능을 차단하고 권한 부족 메시지를 제공한다.
- repository 명명 규칙은 프로젝트/과제 식별이 가능하도록 일관되게 설계한다.

3. 버전 및 형상관리 제공
- 설계 문서는 GitHub repository에서 버전 관리되어야 한다.
- commit 이력, branch, PR, merge 정보를 기반으로 문서 변경 이력을 추적할 수 있어야 한다.
- 사용자는 문서 변경 이력과 승인 상태를 UI에서 확인할 수 있어야 한다.
- Git Graph 또는 유사한 시각화 형태로 형상 흐름을 확인할 수 있어야 한다.
- Git Graph는 모든 브랜치의 커밋을 대상으로 분기/합류를 시각화하며, 날짜 역순(최신 먼저)으로 표시한다.
- Git Graph 구현 상세:
  - Lane 할당: main 브랜치의 first-parent chain → lane 0, 기타 브랜치 → lane 1, 2, ... (프론트엔드에서 재계산)
  - merge 커밋의 second parent를 추적하여 해당 브랜치의 lane을 할당한다.
  - 같은 lane 내 커밋은 수직선으로, 다른 lane 간 연결은 S-커브(cubic bezier)로 표현한다.
  - 브랜치별 파스텔톤 색상을 적용하며, 노드는 원형(7px)으로 표시한다.
  - 커밋 정보는 SHA(7자리), 브랜치 태그, 메시지, 작성자, 날짜 컬럼으로 구성한다.

3-1. 문서 자동 생성 (docgen)
- 시스템은 JIRA/이슈 데이터를 기반으로 설계문서(Markdown)를 자동 생성할 수 있어야 한다.
- 이슈 유형별(요구사항, 설계결정, 기능 등)로 Markdown 파일을 생성한다.
- 자동 생성된 문서는 사용자의 작업 브랜치(worktree)에 commit/push한다.
- 이 시점에서 PR은 생성하지 않는다 (사용자의 작업 브랜치에만 반영).
- 사용자는 Edit 탭에서 자동 생성된 문서를 확인하고 직접 수정할 수 있다.
- 사용자가 문서를 확인/수정한 후 명시적으로 "배포(PR) 요청"을 하면 PR을 생성한다.
- PR 제목과 본문은 LLM(GPT 등)을 활용하여 변경 내용을 요약 생성한다.

3-2. 문서 편집
- 사용자는 웹 UI에서 Markdown 문서를 직접 조회하고 편집할 수 있어야 한다.
- 편집 시작 시 사용자별 작업 브랜치(docs/{userId})가 자동 생성된다.
- 편집 내용의 저장은 commit → push로 처리한다.
- 작업 완료 후 PR 생성 → 승인 → main 반영 흐름을 따른다.
- 문서 목록 UI 좌측에 Main 탭과 작업공간 탭을 제공하여 main 브랜치와 사용자 브랜치의 파일을 구분하여 표시한다.
- 작업공간 탭에서는 origin/main 대비 변경 상태를 색상으로 표시한다 (수정=노랑, 추가=초록, 삭제=빨강).

3-3. 사용자별 독립 작업 공간
- 서버 로컬에서 사용자별 독립된 작업 디렉토리를 제공한다.
- git worktree를 활용하여 하나의 클론에서 사용자별 작업 디렉토리를 분리한다.
- 이를 통해 여러 사용자가 동시에 서로 다른 브랜치에서 작업할 수 있다.
- 구조 예시:
  - repos/{org}/{repo}/                  ← 메인 클론 (main)
  - repos/{org}/{repo}-wt/{userId}/      ← 사용자별 worktree
- Workspace는 캐시로 취급하며, 원격 사용자 브랜치가 Source of Truth이다.
- Workspace TTL: 기본 30분 (설정 변경 가능), 마지막 접근 기준으로 자동 삭제.
- TTL 만료 후에는 사용자 브랜치 기준으로 재생성한다.

3-4. 동시 작업 및 충돌 처리
- 서로 다른 파일을 수정하는 경우 → 각자 독립적으로 PR 생성, 충돌 없이 머지 가능
- 동일 파일을 수정하는 경우 → 선 머지된 PR 기준으로 후 PR에서 merge conflict 발생
- 충돌은 PR 단계에서 감지하고, UI에서 충돌 상태를 표시한다.
- 동일 이슈를 여러 사용자가 동시 편집하는 상황은 이슈 담당자 기준으로 사전 방지한다.
- Rebase 충돌 발생 시: abort → 사용자 변경 diff 표시 → main 기준 reset → 재작업 유도
- 동시 편집 제어: 1사용자=1세션 정책, DB 기반 세션 lock, 다른 세션은 read-only
- 세션 TTL: 기본 30분 (설정 변경 가능), inactivity 기준 자동 해제

3-5. 미완료 작업 처리
- 사용자가 저장하지 않고 종료한 경우, 작업 브랜치와 worktree는 유지한다.
- 다음 로그인 시 "이전에 작업하던 내용이 있습니다" 안내를 제공한다.
- 사용자는 이어서 작업하거나 폐기를 선택할 수 있다.
- 저장(커밋)하지 않은 작업은 workspace TTL 만료 시 소실될 수 있으므로, UI에서 "저장하지 않으면 작업이 소실될 수 있습니다" 경고를 명확히 표시한다.

3-6. PR Merge 후 처리
- 사용자 브랜치(docs/{userId})는 merge 후에도 유지한다.
- Workspace는 삭제한다.
- 다음 접속 시 자동으로 rebase(origin/main 동기화)를 수행하여 바로 다음 작업을 시작할 수 있도록 한다.

4. 소스코드와 연결 관리
- 설계 문서는 관련 소스코드 저장소 또는 코드 경로와 연결되어야 한다.
- 과제(Task)를 기준으로 문서와 코드 간 연관 관계를 조회할 수 있어야 한다.
- 최소한 다음 연결 정보가 관리되어야 한다:
  - Task ID
  - 설계서 repository
  - 관련 코드 repository 또는 코드 경로
  - 관련 PR 정보
- 향후 설계-코드 정합성 검토로 확장 가능한 구조로 설계한다.

5. GitHub 미숙자를 위한 간편 UI 제공
- UI는 GitHub 사용 경험이 부족한 사용자도 쉽게 사용할 수 있도록 과제 중심으로 구성한다.
- GitHub 화면을 직접 노출하기보다, 필요한 기능을 업무 목적에 맞게 단순화하여 제공한다.
- 최소한 아래 기능을 포함해야 한다:
  - 문서 이력 조회
  - 문서 조회 및 편집 (Markdown 에디터)
  - 승인 요청 조회 및 승인/반려
  - 문서 배포(PR) 요청
  - 승인 진행 상황 조회
  - 이력 Git Graph 조회 (전체 브랜치 대상, 브랜치별 lane 시각화, S-커브 분기/합류 표현)
  - 미완료 작업 이어서 작업/폐기
- 사용자는 과제 상세 화면 또는 문서 관리 화면에서 위 기능을 수행할 수 있어야 한다.
- 승인/반려/배포 요청은 내부 UI에서 수행하지만 실제 상태는 GitHub PR에 반영되어야 한다.
- 승인/반려 버튼은 PR 작성자에게는 표시하지 않는다.
- 이미 승인한 사용자의 승인 버튼은 비활성화하고, 반려로 번복은 가능하게 한다.

6. 승인자 처리 규칙
- 승인자는 Task 정보의 auditors 필드에 등록된 사용자로 한다.
- auditors가 비어 있거나 유효한 승인자가 없으면 승인 요청을 생성하거나 승인 절차를 진행하지 않는다.
- 이 경우 사용자에게 “승인자를 먼저 지정하세요” 또는 이에 준하는 명확한 안내 메시지를 제공한다.
- 승인 요청 화면에는 현재 auditors 정보를 표시할 수 있어야 한다.

7. Markdown 문서 및 계층 구조
- 문서는 Markdown(.md) 파일로 관리한다.
- 하나의 설계서는 여러 Markdown 파일로 구성될 수 있다.
- 여러 파일 간 부모/자식 또는 상위/하위 구조를 표현할 수 있어야 한다.
- 문서 구조를 repository 내 폴더 구조 또는 메타데이터로 표현할 수 있어야 한다.
- UI에서는 계층 구조를 탐색 가능하게 표시해야 한다.

8. 승인(PR) 및 배포(Merge) 처리 규칙
- 승인자는 Task 정보의 auditors 필드에 등록된 사용자로 한다.
- auditors가 비어 있거나 유효한 승인자가 없으면 승인 요청을 생성하거나 승인 절차를 진행하지 않는다.
- 이 경우 사용자에게 “승인자를 먼저 지정하세요” 또는 이에 준하는 명확한 안내 메시지를 제공한다.
- 승인 요청 화면에는 현재 auditors 정보를 표시할 수 있어야 한다.
- 승인 요청은 GitHub PR 생성으로 처리한다.
- 승인 처리는 GitHub review/merge 흐름과 연계한다.
- PR 생성시 메시지를 LLM 기반으로 커밋내용을 요약하여 PR 제목과 본문에 자동으로 입력한다.
- LLM 출력은 커밋 및 변경 주요 내역을 간략한 리포트 형태로 제공한다.
- LLM 프롬프트는 외부 파일(예: prompts/pr-summary.txt)로 관리하여 개발자가 직접 수정 가능하도록 한다.
- PR 승인시 UI의 승인요청에 메시지를 보여준다.
- 메시지의 우상단에 [상세보기] 버튼을 배치하고 클릭하면 GitHub PR로 이동한다. 
- 레포 생성시 branch protection을 설정하여 모든 리뷰가 끝나기 전에는 머지 할 수 없도록 한다.
  - Gitea: branch_protections API로 private 레포에서도 무료 지원
  - GitHub Free: private 레포 미지원 → API 레벨에서 머지 전 리뷰 완료 검증으로 보완
- UI 에도 리뷰 진행 상황을 보여 주고 완료 되면 머지 버튼을 활성화 한다.
- 웹훅(pull_request, pull_request_review, push)을 이용하여 머지 가능 상태를 실시간으로 반영한다.
- PR 요청 발생, 머지 가능 상황은 메일로 발송되게한다 (향후 메신저 등을 연계 할 것임)

9. 사용자별 Git 플랫폼 인증
- 사용자 계정 생성 시 Gitea에 동일한 knoxId로 사용자를 자동 등록한다.
- Gitea API 토큰을 자동 생성하여 DB(users.giteaToken)에 저장한다.
- PR 생성, 리뷰, 머지 등 Git 작업은 해당 사용자의 토큰으로 수행한다.
- 관리 작업(레포 생성, 팀 관리, 브랜치 보호 등)은 관리자 토큰으로 수행한다.
- 이메일 중복 시 계정 생성을 차단하고 다른 이메일을 입력하도록 안내한다.

[권장 구현 방향]
- 설계문서는 Gitea(self-hosted)를 원본 저장소로 사용한다.
- 소스코드는 GitHub를 원본 저장소로 유지한다.
- 과제 관리 시스템(Platform-API)이 Gitea/GitHub API와 연계한다.
- 내부 DB에는 Task, 문서 메타데이터, repository 정보, PR 정보, auditor 정보, 문서-코드 매핑 정보를 저장한다.
- UI는 과제 중심 탐색 구조를 갖고, 사용자가 Git 플랫폼을 직접 사용하지 않고도 주요 승인/조회/배포 작업을 할 수 있게 한다.
- 문서 배포 요청은 PR 생성으로 처리한다.
- 승인 처리는 review/merge 흐름과 연계한다.
- 환경 설정만으로 GitHub ↔ Gitea 전환이 가능하도록 API 추상화 계층을 유지한다.


[추가 제약]
- Git 플랫폼(Gitea/GitHub)의 기존 PR/이력/형상관리 기능을 중복 구현하지 않는다.
- 다만 Git 미숙자를 위한 간편한 업무 UI는 별도로 제공한다.
- 구조는 향후 코드 생성 및 설계-코드 정합성 검토 기능으로 확장 가능해야 한다.
- 구현 제안 시 실제 운영 가능한 수준의 구체성을 유지한다.

[인프라 구성]
- Gitea: Docker 컨테이너로 운영 (포트 3300)
  - 설계문서 전용 Git 서버
  - SQLite3 기반 경량 구성
  - private 레포 + branch protection 무료 지원
- GitHub: 소스코드 저장소 (기존 유지)
- 전환 설정: Platform-API의 .env 파일에서 GITHUB_URL을 변경하면 즉시 전환 가능
  - GitHub: GITHUB_URL=https://github.com/
  - Gitea: GITHUB_URL=http://localhost:3300/
